진행하던 프로젝트들의 데이터가 어느 순간 정말 감당하기 어려울 만큼 쌓였습니다.
처음에는 조회가 조금 느려진 정도라 크게 신경 쓰지 않았는데, 시간이 지나니 추가와 수정까지 눈에 띄게 무거워지더라고요. 😅

그중에서도 제일 골치 아팠던 건 바로 **삭제**였어요!
오래된 데이터를 정리하려고 `DELETE`를 돌릴 때마다 테이블 전체가 버거워했거든요.
정리를 해야 테이블이 가벼워지는데, 정리하는 작업 자체가 테이블을 무겁게 만드는 아이러니한 상황이었습니다. 🤔

그래서 결심했습니다! **"이번 기회에 파티셔닝을 제대로 공부하고 적용해 보자!"** 💪

이번 글은 그 과정에서 공부하고 정리한 내용이에요.
파티셔닝이 왜 삭제 문제의 답이 되는지, 그리고 걸기 전에 무엇을 따져봐야 하는지를 중심으로 적어봤습니다.
실제 프로젝트가 **MySQL**이라 예시도 MySQL(InnoDB) 기준으로 적었어요. 테이블 이름과 컬럼은 설명을 위해 만든 예시입니다!

&nbsp;

## 🧹 큰 테이블에서 삭제가 유독 아픈 이유

`DELETE`는 겉보기엔 한 줄짜리 SQL이지만, 안에서 일어나는 일은 생각보다 훨씬 많습니다!

```sql
-- 90일 지난 로그 정리 — 겉보기엔 단순하다
DELETE FROM event_logs
WHERE created_at < NOW() - INTERVAL 90 DAY;
```

InnoDB는 이 쿼리를 **행 단위로** 처리해요. 지워지는 행 하나하나마다 아래 일이 같이 일어납니다.

- 롤백을 위해 **undo 로그**를 남깁니다
- 복제와 복구를 위해 **binlog**에 기록합니다 (row 포맷이면 지운 행 전부!)
- 조건에 걸리는 범위에 **락**을 잡습니다 (REPEATABLE READ에서는 갭 락까지)
- 모든 **보조 인덱스**에서도 해당 항목을 하나하나 지웁니다

그래서 지울 행이 많을수록 트랜잭션이 길어지고, 그동안 같은 범위에 쓰려는 다른 쿼리들은 줄줄이 기다리게 됩니다.
레플리카가 있다면 그 큰 삭제를 그대로 재생하느라 **복제 지연**까지 생기고요!

흔히 쓰는 우회책은 조금씩 나눠서 지우는 방법이에요.

```sql
-- 청크 삭제 — 락 시간을 짧게 쪼갠다
DELETE FROM event_logs
WHERE created_at < NOW() - INTERVAL 90 DAY
ORDER BY id
LIMIT 5000;
-- 영향받은 행이 0이 될 때까지 반복
```

락이 짧아지니 서비스 입장에서는 훨씬 덜 아픕니다. 그런데 곰곰이 생각해 보면 **지우는 총량은 똑같아요.**
undo, binlog, 인덱스 정리 비용이 시간에 나눠서 퍼질 뿐이거든요.

게다가 지운다고 `.ibd` 파일이 줄어들지도 않습니다!
빈 공간은 테이블 안에 그대로 남고, 디스크로 돌려받으려면 테이블을 다시 빌드해야 해요.

> **"오래된 데이터를 행 단위로 지우는 것" 자체가 비싼 일이다.**

이걸 받아들이고 나니 방향이 확 보이기 시작했어요. 💡
행을 하나씩 지우지 말고, **덩어리째 버릴 수 있게** 저장하면 되겠다는 거였죠!

&nbsp;

## 📌 파티셔닝이 하는 일

파티셔닝은 **하나의 논리 테이블을 여러 물리 조각(파티션)으로 나눠서 저장하는 방식**이에요.
애플리케이션 입장에서는 여전히 테이블 하나이고, SQL도 그대로 쓰면 됩니다!
대신 InnoDB는 파티션마다 별도의 테이블스페이스를 둡니다.

이렇게 나눴을 때 얻는 건 크게 두 가지예요.

&nbsp;

### ✂️ 파티션 단위로 버리기

날짜로 파티션을 나눠두면, 오래된 데이터 정리가 이렇게 바뀝니다!

```sql
-- ❌ 행 단위 삭제: 지울 행 수에 비례해서 비싸다
DELETE FROM event_logs WHERE created_at < '2026-07-01';

-- ✅ 파티션 삭제: 해당 조각을 통째로 떼어낸다
ALTER TABLE event_logs DROP PARTITION p202606;
```

`DROP PARTITION`은 행을 하나씩 지우지 않고 그 파티션을 **통째로** 떼어냅니다.
그래서 행 수와 거의 상관없이 끝나고, undo나 행 단위 binlog도 쌓이지 않아요. 디스크 공간도 바로 돌아오고요!

제가 겪던 삭제 문제의 정답이 바로 여기 있었습니다.

&nbsp;

### 🔍 파티션 프루닝

조회할 때 WHERE 조건에 파티션 키가 들어 있으면, MySQL은 **해당 파티션만 골라서 읽습니다.** 이걸 파티션 프루닝이라고 해요!

```sql
EXPLAIN
SELECT * FROM event_logs
WHERE created_at >= '2026-10-01' AND created_at < '2026-10-08';
-- partitions 컬럼: p202610  ← 이번 달 파티션만 본다
```

`EXPLAIN` 결과의 `partitions` 컬럼에 어떤 파티션을 읽는지 나오기 때문에, 프루닝이 되는지 바로 확인할 수 있어요. 아주 편합니다!

참고로 파티셔닝은 **샤딩과는 다릅니다.**
샤딩은 데이터를 여러 DB 서버로 나누는 것이고, 파티셔닝은 서버 한 대 안에서 테이블 하나를 나누는 거예요.
그래서 서버 한 대의 처리량 한계를 넘는 문제라면 파티셔닝으로는 풀리지 않습니다.

&nbsp;

## 🤔 걸기 전에 따져본 것

파티셔닝을 공부하면서 가장 먼저 깨달은 건, **"테이블이 크다"는 것만으로는 파티셔닝의 이유가 되지 않는다**는 점이었어요!

큰 테이블이 느린 원인은 대부분 인덱스나 쿼리에 있거든요.
인덱스를 못 타는 조건, 커버링이 안 돼서 생기는 대량 랜덤 I/O, 습관처럼 쓰는 `SELECT *` 같은 것들이요.
이런 문제는 파티션을 나눠도 그대로 남습니다. 파티션마다 똑같이 느려질 뿐이에요.

그래서 아래 질문들로 정리해 봤습니다.

| 질문 | 파티셔닝이 맞는 경우 |
| --- | --- |
| 데이터에 수명이 있나? | 보관 기간이 지나면 버리는 데이터 (로그, 이벤트, 이력) |
| 주로 어떻게 조회하나? | 대부분 기간 조건으로 조회한다 |
| 무엇이 제일 아픈가? | 대량 삭제·아카이빙이 아프다 |
| 키 조건 없는 조회가 많나? | 적다 (많으면 오히려 느려진다) |

제 경우는 삭제가 가장 큰 문제였고, 정리 대상이 시간 순으로 쌓이는 데이터였어요.
이런 데이터에는 **날짜 기준 RANGE 파티셔닝**이 가장 잘 맞습니다!

다만 테이블이 여러 개다 보니 한 가지 방식으로 통일하지는 않았어요.
**테이블마다 성격을 보고 파티션 키와 나누는 단위를 따로 정했습니다.** 이 부분이 이번 작업의 핵심이었어요.

&nbsp;

## 🔑 테이블마다 키와 단위를 다르게

### 🗝️ 파티션 키는 테이블 성격에 맞게

파티션 키를 정할 때는 "이 테이블에서 날짜가 어디 있지?"보다 **"이 테이블은 무엇을 기준으로 지우고, 무엇을 기준으로 조회하지?"** 를 먼저 물어봐야 하더라고요.

제가 키를 고를 때 본 기준은 세 가지예요.

- **정리 기준과 같은 컬럼인가?** 보관 기간을 판단하는 컬럼이 곧 파티션 키여야 `DROP PARTITION`으로 깔끔하게 버릴 수 있습니다
- **주요 조회 조건에 들어가는 컬럼인가?** 그래야 프루닝이 걸립니다
- **값이 바뀌지 않는 컬럼인가?** 파티션 키 값을 `UPDATE`하면 그 행은 다른 파티션으로 **이동**해요. 내부적으로는 삭제 후 삽입이라, 자주 바뀌는 컬럼을 키로 잡으면 오히려 일이 늘어납니다

예를 들어 로그처럼 쌓이고 나면 바뀌지 않는 데이터라면 **생성 시각**이 자연스러운 키예요.
반면 "언제 생겼는지"보다 **"어느 날짜의 데이터인지"** 로 조회하고 정리하는 테이블이라면, 생성 시각이 아니라 그 기준 날짜 컬럼을 키로 잡는 게 맞습니다.
같은 날짜라도 테이블마다 의미가 다르더라고요!

&nbsp;

### 📆 일 단위와 월 단위

나누는 단위도 테이블마다 다르게 가져갔어요. 어떤 테이블은 **일 단위**, 어떤 테이블은 **월 단위**로 나눴습니다.

| 기준 | 일 단위가 맞는 테이블 | 월 단위가 맞는 테이블 |
| --- | --- | --- |
| 쌓이는 양 | 하루에도 많이 쌓인다 | 상대적으로 적다 |
| 보관 기간 | 짧다 | 길다 |
| 주된 조회 범위 | 하루·며칠 단위 | 몇 주·몇 달 단위 |
| 정리 단위 | 하루치씩 버리고 싶다 | 한 달치씩 버려도 된다 |

월 단위로 나누면 파티션 수가 적어서 관리가 편해요. 대신 한 달치를 한꺼번에 버리기 때문에, 실제 보관 기간이 정해둔 기간보다 최대 한 달 가까이 길어질 수 있습니다.
일 단위는 그 반대예요. 하루치씩 정확하게 버릴 수 있지만, 파티션 수가 많아지고 **매일** 관리해 줘야 합니다.

월 단위 테이블은 이런 모양이에요.

```sql
CREATE TABLE event_logs (
  id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  user_id    BIGINT UNSIGNED NOT NULL,
  event_type VARCHAR(50)     NOT NULL,
  payload    JSON,
  created_at DATETIME        NOT NULL,
  PRIMARY KEY (id, created_at),          -- ✅ 파티션 키를 PK에 포함
  KEY idx_user_created (user_id, created_at)
)
PARTITION BY RANGE COLUMNS (created_at) (
  PARTITION p202608 VALUES LESS THAN ('2026-09-01'),
  PARTITION p202609 VALUES LESS THAN ('2026-10-01'),
  PARTITION p202610 VALUES LESS THAN ('2026-11-01'),
  PARTITION p202611 VALUES LESS THAN ('2026-12-01'),
  PARTITION pmax    VALUES LESS THAN (MAXVALUE)
);
```

일 단위 테이블은 경계값만 하루씩 잘게 잡으면 됩니다.

```sql
CREATE TABLE request_logs (
  id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  path       VARCHAR(255)    NOT NULL,
  status     SMALLINT        NOT NULL,
  created_at DATETIME        NOT NULL,
  PRIMARY KEY (id, created_at),
  KEY idx_path_created (path, created_at)
)
PARTITION BY RANGE COLUMNS (created_at) (
  PARTITION p20261014 VALUES LESS THAN ('2026-10-15'),
  PARTITION p20261015 VALUES LESS THAN ('2026-10-16'),
  PARTITION p20261016 VALUES LESS THAN ('2026-10-17'),
  -- ... 며칠 앞까지 미리
  PARTITION pmax      VALUES LESS THAN (MAXVALUE)
);
```

파티션 이름에 날짜를 그대로 넣어두면 어떤 파티션이 언제 데이터인지 한눈에 보이고, 자동화 코드에서 이름을 계산하기도 쉬워요!

### 🧷 PK와 외래 키 제약

키를 정하고 나면 바로 걸리는 게 **PK**입니다!

MySQL에는 **"모든 유니크 키(PK 포함)는 파티션 키 컬럼을 포함해야 한다"** 는 규칙이 있어요.
파티션마다 인덱스가 따로 있어서, 파티션을 넘나드는 유일성은 DB가 보장해 줄 방법이 없거든요.
그래서 위 예시들처럼 `PRIMARY KEY (id)`를 `PRIMARY KEY (id, created_at)`로 바꿔야 합니다.

이 변경에는 두 가지 의미가 따라와요.

- `id` 단독의 유일성은 이제 **DB 제약이 아니라 AUTO_INCREMENT가 지켜주는 것**이 됩니다. 실무에서 문제 될 일은 드물지만, `id` 값을 직접 넣는 코드가 있다면 꼭 확인해 주세요!
- 이메일처럼 **비즈니스 유니크 키**가 있는 테이블이라면 파티셔닝과 잘 맞지 않습니다. 유니크 키에 날짜를 섞으면 의미 자체가 바뀌니까요.

그리고 하나 더 있습니다. **파티션 테이블은 외래 키를 쓸 수 없어요!**
다른 테이블을 참조할 수도, 참조당할 수도 없습니다.
이력 데이터는 보통 외래 키가 꼭 필요하지 않지만, 걸려 있었다면 애플리케이션 쪽에서 정합성을 챙기도록 바꿔야 해요.

## 🛠️ 운영 중인 테이블에 적용하기

새로 만드는 테이블이면 위처럼 만들면 끝이지만, 이미 데이터가 잔뜩 쌓인 테이블은 이야기가 달라집니다.

```sql
-- ⚠️ 기존 테이블을 바로 파티셔닝으로 바꾸기
ALTER TABLE event_logs
PARTITION BY RANGE COLUMNS (created_at) ( ... );
```

이 `ALTER`는 테이블 전체를 **새로 복사해서 다시 만듭니다.**
파티셔닝 변경은 온라인 DDL(INPLACE)을 지원하지 않아서, 복사하는 동안 **쓰기가 막혀요!**
데이터가 많은 테이블에 서비스 시간에 돌렸다가는 그 시간 내내 쓰기 장애가 되는 거죠.

그래서 큰 테이블은 보통 이렇게 옮깁니다.

```sql
-- 1) 파티셔닝된 새 테이블을 만든다
CREATE TABLE event_logs_new ( ... ) PARTITION BY RANGE COLUMNS (created_at) ( ... );

-- 2) 기존 데이터를 구간별로 나눠 옮긴다 (한 번에 다 옮기지 않는다)
INSERT INTO event_logs_new
SELECT * FROM event_logs
WHERE created_at >= '2026-08-01' AND created_at < '2026-08-08';
-- ... 구간을 밀어가며 반복

-- 3) 옮기는 동안 들어온 데이터까지 맞춘 뒤, 이름을 한 번에 바꾼다
RENAME TABLE event_logs     TO event_logs_old,
             event_logs_new TO event_logs;
```

`RENAME TABLE`은 여러 테이블을 원자적으로 바꿔주기 때문에, 애플리케이션은 교체되는 순간을 거의 느끼지 못해요!
다만 **옮기는 도중에 들어오는 쓰기**를 어떻게 따라잡을지는 미리 정해둬야 합니다.
그 구간만 다시 복사하거나, `pt-online-schema-change` 같은 온라인 스키마 변경 도구에 이 과정을 맡기는 방법이 있어요.

교체가 끝나도 `event_logs_old`는 바로 지우지 마세요! 검증이 끝날 때까지 남겨두는 게 마음 편합니다. 😌

&nbsp;

## 🗓️ 파티션은 만들고 끝이 아니다

RANGE 파티션은 **시간이 흐르는 동안 계속 관리해 줘야 합니다.**
이 부분을 자동화해 두지 않으면 나중에 꼭 사고가 나더라고요.

&nbsp;

### ➕ 앞으로 쓸 파티션 미리 만들기

마지막에 둔 `pmax`는 "범위를 벗어난 데이터를 받아주는 안전망"이에요.
이게 없으면 마지막 파티션 범위를 넘는 날짜가 들어오는 순간 INSERT가 바로 실패합니다!

```text
ERROR 1526 (HY000): Table has no partition for value ...
```

새 파티션은 `pmax`를 쪼개서 만들어요.

```sql
-- pmax를 "12월 파티션 + 새 pmax"로 나눈다
ALTER TABLE event_logs
REORGANIZE PARTITION pmax INTO (
  PARTITION p202612 VALUES LESS THAN ('2027-01-01'),
  PARTITION pmax    VALUES LESS THAN (MAXVALUE)
);
```

여기서 중요한 포인트! **`pmax`가 비어 있을 때 쪼개야 합니다.**
`REORGANIZE`는 대상 파티션의 데이터를 다시 쓰거든요. 비어 있으면 금방 끝나지만, 이미 데이터가 쌓였다면 그만큼 무거운 작업이 돼요.
그래서 파티션은 미리 만들어 둡니다. 월 단위 테이블은 **한두 달**, 일 단위 테이블은 **며칠에서 일주일** 정도 앞서 두면 배치가 하루 이틀 실패해도 버틸 수 있어요.

&nbsp;

### 🗑️ 보관 기간 지난 파티션 버리기

```sql
-- 보관 기간이 지난 달을 통째로 버린다
ALTER TABLE event_logs DROP PARTITION p202608;

-- 데이터만 비우고 파티션 정의는 남기고 싶다면
ALTER TABLE event_logs TRUNCATE PARTITION p202608;
```

이 두 작업을 사람이 손으로 하면... 언젠가는 꼭 빠뜨립니다. 😂 일 단위 테이블이 있다면 더더욱요!
배치로 돌려두는 게 안전해요. 테이블마다 단위와 보관 기간이 다르니, 정책을 한곳에 모아두면 관리하기 편합니다.
예를 들어 NestJS라면 이런 식으로 둘 수 있어요.

```typescript
// 테이블마다 단위·미리 만들 개수·보관 기간을 따로 둔다 (예시)
const PARTITION_POLICIES = [
  { table: 'request_logs', unit: 'day',   ahead: 7, retention: 30 },
  { table: 'event_logs',   unit: 'month', ahead: 2, retention: 3 },
] as const;

// 일 단위 테이블이 있으니 매일 새벽에 돈다
@Cron('0 3 * * *')
async rotatePartitions() {
  for (const policy of PARTITION_POLICIES) {
    const until = dayjs().add(policy.ahead, policy.unit).startOf(policy.unit);
    const expired = dayjs().subtract(policy.retention, policy.unit).startOf(policy.unit);

    await this.ensurePartitionsUntil(policy, until);   // 빠진 날짜까지 전부 채워서 만든다
    await this.dropPartitionsBefore(policy, expired);  // 보관 기간 지난 파티션 정리
  }
}
```

여기서 `ensurePartitionsUntil`은 "다음 파티션 하나"가 아니라 **목표 날짜까지 빠진 것을 전부** 만들게 하는 게 포인트예요. 배치가 며칠 실패한 뒤 돌아와도 구멍 없이 따라잡을 수 있거든요!

현재 파티션 상태는 `INFORMATION_SCHEMA`에서 볼 수 있어요. 배치가 제대로 돌았는지 확인하는 용도로도 딱 좋습니다!

```sql
SELECT partition_name, partition_description, table_rows
FROM information_schema.partitions
WHERE table_schema = DATABASE() AND table_name = 'event_logs'
ORDER BY partition_ordinal_position;
```

`table_rows`는 추정치라 정확한 행 수는 아니지만, **`pmax`에 데이터가 들어오기 시작했는지** 감시하는 데는 충분해요.
거기에 데이터가 보인다면 파티션 생성이 밀렸다는 신호거든요!

&nbsp;

## ⚠️ 걸고 나서 알게 되는 것들

파티셔닝이 삭제 문제는 깔끔하게 풀어줬지만, 공짜는 아니었습니다.
미리 알아두면 좋을 것들을 정리해 봤어요!

&nbsp;

### 🐢 파티션 키 없는 조회는 오히려 느려진다

모든 인덱스는 **파티션별로 따로** 존재합니다. 전체를 아우르는 글로벌 인덱스가 없어요!

```sql
-- ❌ created_at 조건이 없다 → 모든 파티션의 인덱스를 각각 뒤진다
SELECT * FROM event_logs WHERE user_id = 42 ORDER BY created_at DESC LIMIT 20;

-- ✅ 기간을 함께 주면 해당 파티션만 본다
SELECT * FROM event_logs
WHERE user_id = 42
  AND created_at >= '2026-10-01'
ORDER BY created_at DESC LIMIT 20;
```

그래서 파티셔닝을 걸고 나면 **자주 쓰는 쿼리에 기간 조건을 넣는 작업**이 함께 따라옵니다.
화면에서 "최근 N일"처럼 기본 기간을 두는 식으로요!

&nbsp;

### 🧮 함수로 감싸면 프루닝이 안 된다

```sql
-- ❌ 컬럼을 함수로 감싸면 프루닝이 깨질 수 있다
WHERE DATE(created_at) = '2026-10-16'

-- ✅ 범위 조건으로 쓴다
WHERE created_at >= '2026-10-16' AND created_at < '2026-10-17'
```

인덱스를 탈 때와 똑같은 원칙이에요. 습관처럼 범위로 쓰는 게 제일 안전합니다!

&nbsp;

### 📦 파티션 개수는 보관 기간이 정한다

파티션마다 파일과 메타데이터가 생기기 때문에, 개수가 많아지면 그 자체가 부담이 돼요.
일 단위 테이블은 **보관 일수만큼** 파티션이 생기니, 보관 기간이 길수록 개수가 빠르게 늘어납니다.
MySQL은 테이블당 파티션을 최대 8,192개까지 허용하지만, 그 한도에 가기 훨씬 전부터 파티션 관련 DDL이 무거워지더라고요.

그래서 모든 테이블을 일 단위로 맞추지 않고, **정말 일 단위가 필요한 테이블만** 일 단위로 나눴어요.
나머지는 월 단위로 두는 게 관리 부담과 정리 정밀도 사이에서 적당한 균형이었습니다.

처음에는 파티셔닝을 **"큰 테이블을 빠르게 만드는 기술"** 로만 알고 있었는데, 직접 공부하고 적용해 보니 실제로는 **"데이터의 수명을 관리하는 기술"** 에 훨씬 가깝더라고요.

- ✅ 오래된 데이터를 행 단위로 지우는 대신, **파티션을 통째로 버리는 구조**로 바꿀 수 있습니다
- ✅ 파티션 키와 단위(일/월)는 **테이블 성격에 맞게 따로** 정하는 게 핵심입니다
- ✅ 그 대가로 PK·유니크 키·외래 키 설계, 파티션 키를 포함한 쿼리, 주기적인 파티션 관리가 따라옵니다

데이터가 계속 쌓이는 테이블 때문에 고민하고 계신다면, 먼저 **"이 데이터에 수명이 있는가?"** 부터 따져보세요.
그 답이 "예"라면 파티셔닝이 분명 좋은 선택이 되어줄 거예요! 🚀✨
